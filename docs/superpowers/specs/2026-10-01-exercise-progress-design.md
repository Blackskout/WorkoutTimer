# Прогресс в упражнении — дизайн

**Дата:** 2026-10-01
**Ветка:** `feature/exercise-progress`

## Проблема

Сессия тренировки хранит только время начала, конца и длительность (`workout_sessions`). Фактические веса и повторы нигде не записываются: правка плиток на экране подхода меняет **шаблон** упражнения (`WorkoutExecutionViewModel.updateExerciseWeightAndReps`, `WorkoutExecutionViewModel.kt:390`), прежнее значение затирается. Ответить на вопрос «растёт ли мой присед» приложение не может.

Вторая помеха — идентичность упражнения. `updateWorkout` удаляет упражнения тренировки и вставляет заново (`WorkoutRepositoryImpl.kt:41`), поэтому id упражнения меняется при каждом сохранении в редакторе; опереться на него нельзя. Один и тот же присед в двух тренировках — две несвязанные строки.

Третья — единицы. Всё подписано «кг», хотя на кроссовере нагрузка — номер плиты, а поверх плиты пользователь иногда ставит гантель 2–3 кг.

## Цель

Экран прогресса упражнения: график лучшего подхода по сессиям и список всех подходов. Упражнения живут в справочнике — переименование не рвёт историю, одно упражнение из разных тренировок сходится в один график. У упражнения честная единица нагрузки.

## Решения пользователя

Приняты в диалоге 30.09–01.10.2026:

1. Главный вопрос статистики — прогресс в конкретном упражнении (не регулярность, не тоннаж, не «что было в прошлый раз» как отдельная цель).
2. Упражнения — записи **справочника**. В редакторе тренировки под полем названия подсказки из справочника; новое название само попадает в справочник при сохранении.
3. Изменение названия упражнения в редакторе — **замена** упражнения в этой тренировке, не переименование записи справочника. Переименование — только на экране «Упражнения».
4. Неиспользуемые записи справочника (нет ни в одной тренировке и нет подходов) удаляются сами. Кнопки «Удалить» нет.
5. Единица нагрузки у записи справочника: **кг**, **плита**, **без веса**.
   - Плита: номер 1–30 плюс необязательная добавка 0–10 кг с шагом 0.5 (гантель поверх стопки).
   - Без веса: только повторы, дополнительного веса нет.
6. Фактический подход — значения с плиток экрана подхода в момент «Закончить подход». Подтверждения после подхода нет.
7. Точка на графике — **лучший подход** сессии.
8. Прогресс открывается с экрана «Упражнения» и из истории тренировки (разворот сессии → тап по упражнению).

## Вне рамок

- Регулярность, серии, итоги недели, тоннаж.
- Объединение дублей справочника («Присед» / «Приседания»). Переименование в занятое название запрещено.
- Сохранение незавершённой тренировки и переживание смерти процесса — отдельная отложенная задача; подходы, как и сессия, пишутся только при завершении.
- Подходы в файле экспорта. Сессии в экспорт не попадают и сейчас (`ExportData`); бэкап устройства переносит базу целиком.
- Задним числом подходы для старых сессий не выдумываются: график начинается с первой тренировки после обновления.

## Модель данных

Одна миграция **7 → 8** создаёт всё сразу, включая таблицу подходов: каждый релиз без записи подходов — потерянные для графика тренировки, поэтому запись включается в первом же PR.

### `exercise_catalog` (новая)

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `name` | TEXT NOT NULL | название для показа |
| `nameKey` | TEXT NOT NULL, UNIQUE-индекс | нормализованное название |
| `unit` | TEXT NOT NULL DEFAULT 'KG' | `KG` / `PLATE` / `BODYWEIGHT` |

**Ключ названия** считается только в Kotlin, одной функцией `exerciseNameKey(name)` на весь код: `trim()`, схлопывание пробельных серий в один пробел (регулярка `[\s\p{Z}]+`: голый `\s` видит только ASCII, `\p{javaWhitespace}` не считает пробелом неразрывный U+00A0, а флаг `(?U)` не поддерживается движком регулярок Android — ICU бросает исключение, JVM-тесты этого не видят), `lowercase(Locale.ROOT)`, `ё → е`. SQLite `LOWER()` складывает только ASCII, поэтому сравнение кириллицы в SQL запрещено — везде (редактор, импорт, переименование, миграция) ищем по `nameKey`, посчитанному в Kotlin.

**Пустое название** всюду заменяется на «Без названия» **до** вычисления ключа — иначе пустая группа и настоящее упражнение «Без названия» получили бы один ключ позже, чем сгруппировались, и UNIQUE-индекс уронил бы миграцию. В миграции строка захардкожена (ресурсы там недоступны), в остальном коде — из `strings.xml` с тем же текстом.

### `exercises` (изменение)

- `catalogId INTEGER NOT NULL DEFAULT 0` — ссылка на справочник. Внешнего ключа нет: SQLite не добавляет FK без пересоздания таблицы, а остальная схема живёт без FK. Индекс `index_exercises_catalogId`.
- `extraWeight REAL NOT NULL DEFAULT 0` — добавка к плите в шаблоне. Для `KG` и `BODYWEIGHT` всегда 0.
- `name` остаётся: его читает поиск (`WorkoutDao.searchWorkouts`, `WorkoutDao.kt:58`). Переименование в справочнике обновляет и `exercises.name` всех ссылающихся строк.

Сущность объявляет `@ColumnInfo(defaultValue = …)` для обеих колонок, чтобы схема сущности совпадала с тем, что создаёт `ALTER TABLE … DEFAULT`. То же для `exercise_catalog.unit` (`'KG'`) и `session_sets.extraWeight` (`'0'`).

**Инвариант `catalogId > 0`.** `DEFAULT 0` нужен только для `ALTER TABLE`; у `ExerciseEntity.catalogId` нет значения по умолчанию в Kotlin, и все три пути вставки упражнений (`WorkoutRepositoryImpl.kt:52`, `:83`, `ExportImportRepositoryImpl.kt:104`) обязаны его проставить. Страховка на случай нарушения — в «Правилах данных» (завершение тренировки).

### `session_sets` (новая)

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | порядок записи внутри сессии = порядок id |
| `sessionId` | INTEGER NOT NULL, FK → `workout_sessions(id)` ON DELETE CASCADE | |
| `catalogId` | INTEGER NOT NULL, FK → `exercise_catalog(id)` ON DELETE RESTRICT | |
| `weight` | REAL NOT NULL | кг, номер плиты или 0 для `BODYWEIGHT` |
| `extraWeight` | REAL NOT NULL DEFAULT 0 | добавка к плите |
| `reps` | INTEGER NOT NULL | |
| `unit` | TEXT NOT NULL | единица **на момент подхода** |

Индексы по `sessionId` и `catalogId`. FK у новой таблицы ничего не стоят и страхуют главное правило: `RESTRICT` не даст автоочистке справочника удалить запись, у которой есть подходы.

**FK действительно работают.** Room 2.8.4, увидев `@ForeignKey` хоть у одной сущности, включает `PRAGMA foreign_keys = ON` при открытии базы и прогоняет `foreign_key_check` после миграции; во время самой миграции FK выключены. Значит, вставка подхода с несуществующим `catalogId` роняет транзакцию — отсюда инвариант выше и страховка при завершении.

**Точный SQL.** `CREATE TABLE`, `CREATE INDEX` и текст FK в миграции копируются из выгруженного `app/schemas/.../8.json`, а не пишутся от руки. Имена индексов — те, что генерирует Room: `index_exercise_catalog_nameKey` (UNIQUE), `index_exercises_catalogId`, `index_session_sets_sessionId`, `index_session_sets_catalogId`. Номера подхода нет намеренно: между упражнениями можно прыгать (`moveToSelectedExercise`, `WorkoutExecutionViewModel.kt:334`) и возвращаться, «подход N» не уникален.

### Доменные модели

- `ExerciseUnit { KG, PLATE, BODYWEIGHT }`.
- `Exercise` получает `catalogId`, `unit`, `extraWeight`.
- **Как читается единица (с E2).** В E1 все записи справочника — `KG`, поэтому `Exercise.unit` там всегда `KG` и связь не нужна. С E2 `WorkoutWithExercises` (`WorkoutWithExercises.kt:10`) переходит на вложенную связь: `@Relation(entity = ExerciseEntity::class, …) val exercises: List<ExerciseWithCatalog>`, где `ExerciseWithCatalog` — `@Embedded ExerciseEntity` + `@Relation(parentColumn = "catalogId", entityColumn = "id") ExerciseCatalogEntity?`. Это затрагивает `getWorkoutById`, поиск, маппер виджета и `WorkoutMapper`; `unit` берётся из связи, при её отсутствии — `KG`.
- `CatalogExercise(id, name, unit)`, `SessionSet(id, sessionId, catalogId, weight, extraWeight, reps, unit)`.

## Миграция 7 → 8

Пишется на Kotlin внутри `Migration.migrate(connection)` (как и остальные после PR #20), в порядке:

1. Создать `exercise_catalog`, `session_sets` с индексами; добавить в `exercises` колонки `catalogId`, `extraWeight`.
2. Удалить упражнения-«призраки»: `DELETE FROM exercises WHERE workoutId NOT IN (SELECT id FROM workouts)`. Их оставляло `deleteWorkout` (`WorkoutDao.kt:33`), в интерфейсе они нигде не видны.
3. `SELECT id, name FROM exercises`. Пустое после `trim()` название (могло прийти из импорта — редактор пустые отсекает) сначала заменяется на «Без названия» и записывается в `exercises.name`; **затем** всё группируется по `exerciseNameKey(name)`.
4. На каждую группу — строка справочника: `name` — название первого по `id` упражнения группы (с обрезанными краями), `unit = 'KG'`.
5. `UPDATE exercises SET catalogId = ? WHERE id = ?` для каждой строки. Пустая таблица `exercises` — допустимый вход: справочник просто остаётся пустым.

`workout_sessions` не трогается, включая сессии удалённых тренировок — они останутся основой истории. Версия базы 8 добавляется в `ALL_MIGRATIONS` (`AppDatabase.kt`), схема `8.json` коммитится.

## Правила данных

**Где живут транзакции.** В `@Transaction`-методах по умолчанию интерфейса `WorkoutDao` — так уже сделан `insertWorkoutWithExercises` (`WorkoutDao.kt:69`). Репозиторий по-прежнему держит только DAO; `AppDatabase` в него не внедряется. Автоочистка справочника вызывается внутри той же транзакции, последним шагом.

- **Удаление тренировки** — одна транзакция: упражнения тренировки, сама тренировка, автоочистка справочника. Сессии и подходы не удаляются никогда.
- **Сохранение тренировки** (`addWorkout`, `updateWorkout`) — одна транзакция: для каждого упражнения найти запись справочника по `nameKey` или создать новую (`unit = KG`), проставить `catalogId`, затем автоочистка. В `exercises.name` пишется **название из справочника**, а не набранный текст: «присед » при записи «Присед» сохраняется как «Присед». Два упражнения с одним ключом в одном сохранении находят одну запись (создаётся максимум одна). Сейчас оба пути не транзакционны (`WorkoutRepositoryImpl.kt:41`, `:80`) — чинится здесь же. Сохранение в редакторе оборачивается в перехват ошибок со снекбаром (`CreateWorkoutViewModel.kt:97-129` сейчас его не имеет).
- **Автоочистка справочника:** `DELETE FROM exercise_catalog WHERE id NOT IN (SELECT catalogId FROM exercises) AND id NOT IN (SELECT catalogId FROM session_sets)`. Вызывается после сохранения, удаления и импорта.
- **Завершение тренировки** — одна транзакция: `insertSession` (теперь возвращает id) и все подходы сессии. Заменяет `addWorkoutSession` (`WorkoutRepositoryImpl.kt:127`). **Сессия не должна потеряться из-за подходов**: если у подхода `catalogId == 0` или такой записи нет, транзакция находит-или-создаёт запись по `nameKey` названия упражнения и пишет подход в неё. Подход, который так и не удалось привязать, отбрасывается, сессия пишется всё равно.
- **Импорт** — одна транзакция на весь файл (сейчас не атомарен): сбой посреди файла откатывает всё. Найти-или-создать справочник по `nameKey`; упражнения с пустым названием пропускаются и **учитываются в `skippedCount`**. Если запись справочника уже есть, её единица главнее единицы из файла. Список существующих названий берётся разовым `suspend`-запросом, а не `getAllWorkouts().first()` (`ExportImportRepositoryImpl.kt:92`) — чтение Flow внутри транзакции не делаем.

## E1 — справочник, миграция, запись подходов

Первый PR, целиком про сохранность данных. Внешне ничего не меняется, но справочник собирается и подходы начинают копиться. Подсказки в редакторе — чистый интерфейс, данные не трогают — перенесены в E2, чтобы первый PR был уже.

### Запись подходов

`WorkoutExecutionViewModel`:

- В начале `onExerciseFinished()` (`:273`), **до** перехода к отдыху или следующему упражнению, из состояния `Active` снимается `RecordedSet(catalogId, weight, extraWeight, reps, unit)` и кладётся в список в памяти. Так захватывается и последний подход тренировки: `moveToNextExercise()` (`:295`) на последнем упражнении сразу пишет сессию.
- Записываются только подходы, закрытые кнопкой «Закончить подход». Перескок на другое упражнение ничего не пишет; вернулся и доделал — подходы дописываются в порядке нажатий. Подходов может быть меньше плана.
- При завершении — `finishSession(…, sets)` одной транзакцией. Выход без завершения не пишет ничего (как сейчас).
- **Двойное нажатие.** На последнем подходе запись идёт в корутине, а состояние остаётся `Active`, пока она не закончится (`WorkoutExecutionViewModel.kt:310-327`). Синхронный флаг «идёт завершение» ставится до запуска корутины; пока он поднят, `onExerciseFinished` ничего не делает — второй подход и вторая сессия не пишутся.
- **Сбой завершения.** Запись оборачивается в перехват ошибок. При сбое подходы остаются в памяти, флаг снимается, состояние остаётся на последнем подходе, на экране выполнения (появляется `SnackbarHost`) — снекбар «Не удалось сохранить тренировку». Повторное «Закончить подход» пробует снова без повторной записи последнего подхода.
- **Правка плиток** по-прежнему меняет шаблон, но порядок меняется: сначала обновляется состояние экрана, потом идёт запись в базу. Сейчас наоборот (`updateExerciseWeightAndReps`, запись на `:393`, состояние на `:404`), и быстрое «Закончить подход» сразу после правки записало бы старые значения. Правка во время отдыха относится к следующему подходу — `onRestFinished` строит `Active` из обновлённого упражнения.
- `Active` получает `extraWeight` (в E1 всегда 0, UI для него в E2).

### Экспорт и импорт в E1

Формат файла не меняется. Импорт переходит на найти-или-создать справочник и одну транзакцию.

### Что не затронуто

Поиск (читает `exercises.name`, который синхронизирован), пропуск и отмена пропуска, виджет (показывает только число упражнений и длительность) — работают как раньше; меняется только маппинг `WorkoutWithExercises`.

## E2 — подсказки, история с подходами, экран «Упражнения», единицы

### Подсказки в редакторе

`CreateWorkoutViewModel` подписывается на справочник. Под полем «Название упражнения» в шторке упражнения — до 5 записей, чей `nameKey` содержит ключ введённого текста; сортировка: сначала начинающиеся с запроса, потом по алфавиту. Подсказок нет, если поле пустое или введённое название точно совпадает с записью. Тап по подсказке подставляет название записи. `catalogId` через состояние редактора не протаскивается: связь находится при сохранении по `nameKey`. А вот `extraWeight` протаскивается: у `ExerciseItem` сейчас его нет, и без него сохранение в редакторе обнуляло бы добавку.

### История тренировки

Карточка сессии (`WorkoutHistoryScreen.kt`) разворачивается по тапу: подходы, сгруппированные по упражнениям в порядке первого появления, например «Присед — 60 кг × 8 · 60 × 8 · 62.5 × 6». Строка упражнения ведёт на прогресс (активна с E3). Сессия без подходов (до обновления) не разворачивается и подписана «подходы не записывались».

### Экран «Упражнения»

Иконка в шапке списка тренировок рядом с поиском. Список справочника по алфавиту с поиском; строка — название и последний лучший подход с давностью («60 кг × 8 · 3 дн. назад»), либо «ещё не делали». Тап — прогресс (с E3). Меню строки:

- **Переименовать** — меняет `name`, `nameKey` записи и `exercises.name` ссылающихся строк одной транзакцией. Если новый ключ занят другой записью — отказ с сообщением «Такое упражнение уже есть».
- **Единица: кг / плита / без веса.** Прошлые подходы сохраняют свою единицу. Шаблоны упражнений с этой записью приводятся к новой единице:
  - → `PLATE`: `weight` округляется до ближайшего целого в 1..30, `extraWeight = 0`;
  - → `KG`: `weight` сохраняет число, `extraWeight = 0`;
  - → `BODYWEIGHT`: `weight = 0`, `extraWeight = 0`.

Редактор тренировки единицу показывает (подпись барабана), но не меняет.

### Единицы в интерфейсе

| Единица | Барабаны (редактор, шторка веса на экране подхода) | Плитка на экране подхода | Строка на экране отдыха |
|---|---|---|---|
| `KG` | кг 0–300 шаг 0.25 (как сейчас, `WeightValues`, `WheelPicker.kt:51`) | «60» / «кг» | «60 кг · 8 повторений» |
| `PLATE` | плита 1–30 шаг 1; +кг 0–10 шаг 0.5 | «5» / «плита» или «плита +2 кг» | «плита 5 +2 кг · 12 повторений» |
| `BODYWEIGHT` | только повторы | плитки веса нет | «12 повторений» |

Места, где сейчас зашито «кг»: `WeightRepsSheet.kt:61`, `CreateWorkoutScreen.kt` (барабан и строка упражнения), `WorkoutExecutionScreen.kt` (плитка и строка отдыха). Все подписи — через ресурсы.

**Формат подхода** (одна функция на всё приложение): `KG` — «60 кг × 8», в перечислении следующих подходов вес без единицы («60 × 8»); `PLATE` — «плита 5 × 12», «плита 5 +2 кг × 12»; `BODYWEIGHT` — «12».

### Экспорт и импорт в E2

`ExportExercise` получает `unit: String = "KG"` и `extraWeight: Double = 0.0`. `ignoreUnknownKeys` уже включён, старые файлы читаются как `KG`.

## E3 — экран прогресса

Маршрут `exercise_progress/{catalogId}`. Сверху вниз:

1. **Шапка**: название, справа подпись единицы.
2. **Главная цифра** — лучший подход за всё время в текущей единице («62.5 кг × 6»), под ней изменение за выбранный период: разница между лучшим подходом последней и первой сессии периода («+2.5 кг за 3 мес»; для плиты «+1 плита» или «+1 кг», если плита та же; для без веса «+2 повт»). Цвет текстовый, без «зелёный = хорошо».
3. **График** — одна линия.
   - Ось X — даты сессий (`finishedAt`), реальная шкала времени: перерывы видны.
   - Ось Y — уровень лучшего подхода сессии: `KG` — вес; `BODYWEIGHT` — повторы; `PLATE` — `плита + добавка / 11`: добавка поднимает точку внутри промежутка до следующей плиты, но никогда до неё не достаёт (добавка ≤ 10). Подписи оси — целые значения.
   - Линия 2dp цвета акцента, точки ≥ 8dp с кольцом цвета фона, сетка и оси приглушённые, легенды нет — линия одна, её называет шапка. Одна ось Y.
   - Тап по точке выделяет её, показывает подпись «26 сен · 60 кг × 8» и подсвечивает строку сессии в списке. Зона попадания шире точки.
   - Рисуется своим Canvas в Compose (как `RestRing`); библиотека графиков не подключается.
4. **Период**: 1 мес / 3 мес / всё. По умолчанию 3 мес.
5. **Список сессий** — все подходы упражнения по датам, новые сверху; это же табличная замена графика для TalkBack.

**В графике только подходы в текущей единице упражнения.** Если были подходы в других единицах, под графиком строка «Подходы в других единицах — в списке ниже»; в списке они показаны со своими подписями.

**Мало данных:** 0 сессий — пустое состояние «Сделайте упражнение — здесь появится прогресс»; меньше 2 точек в периоде — главная цифра и список без графика.

**Лучший подход сессии** (чистая функция, одна на приложение):

- `KG`: больше `weight`, при равенстве больше `reps`;
- `PLATE`: больше `weight`, затем больше `extraWeight`, затем больше `reps`;
- `BODYWEIGHT`: больше `reps`.

Считается в Kotlin по подходам сессии в текущей единице.

## Ошибки и краевые случаи

- Сбой записи (сохранение, удаление, завершение, переименование) — снекбар, как в списке тренировок (`ListWorkoutViewModel.launchGuarded`); приложение не падает, транзакция откатывается целиком.
- Сбой миграции на устройстве — приложение закрывается, данные не стираются: destructive fallback оставлен только для версий 2 и 4 (PR #20).
- Одна запись справочника дважды в одной тренировке — допустимо, подходы обеих строк пишутся в одну запись.
- Переименование в занятое название — отказ с сообщением, ничего не меняется.
- Удалённая тренировка: её сессии и подходы остаются, прогресс упражнения их показывает; история тренировки для удалённой тренировки недоступна, как и сейчас.
