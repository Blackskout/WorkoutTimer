# Свёрнутая тренировка (мини-плеер) — дизайн

**Дата:** 2026-10-01
**Ветка:** `feature/minimized-workout`

## Проблема

Идущая тренировка живёт только на экране выполнения. Вся сессия — состав, индекс, закрытые подходы, таймер отдыха, учёт простоя — хранится во `WorkoutExecutionViewModel` и умирает вместе с его записью навигации: `onCleared()` (`WorkoutExecutionViewModel.kt:293`) снимает wakelock, гасит уведомление и отпускает отметку `ActiveWorkoutTracker`. «Назад» на экране выполнения — только выход с подтверждением (`WorkoutExecutionScreen.kt:94`, `:138`). Посмотреть посреди тренировки другую тренировку (состав, веса, прошлые результаты) и взять оттуда упражнение нельзя, не потеряв текущую.

Вторая помеха — тап по тренировке в списке сразу её запускает (`NavGraph.kt:60`). Пользователь часто открывает тренировку «просто посмотреть», и старт по тапу ему мешает.

## Цель

Тренировка сворачивается, как трек в музыкальном плеере: «Назад» уводит с экрана выполнения, а сессия продолжает идти и видна плашкой внизу всех остальных экранов. Тап по тренировке в списке открывает экран просмотра; оттуда можно начать тренировку или, если другая уже идёт, добавить упражнение в сегодняшнюю.

## Решения пользователя

Приняты в диалоге 01.10.2026 (выбран вариант B — «как плеер в музыкальном приложении», а не «подсмотреть изнутри тренировки»):

1. «Назад» (системный и стрелка в шапке) на экране выполнения **сворачивает** тренировку без диалога. Сессия продолжает жить.
2. Свёрнутая тренировка — **плашка внизу** (не плавающее окно), видна на всех экранах, кроме самого экрана выполнения. Название тренировки + статус: отдых с отсчётом («Отдых 01:18»), подход («Подход 2 из 4 · Жим лёжа»), отдых закончился («Пора: подход 2»). Маленькое кольцо слева. Тап — вернуться на экран выполнения.
3. На плашке крестик × → диалог «Выйти из тренировки? Прогресс не будет сохранён.» → сессия сбрасывается без записи. То же действие — в меню ⋮ экрана выполнения («Выйти без сохранения»), потому что «Назад» больше не выходит.
4. Тап по тренировке в списке открывает **новый экран просмотра**: упражнения с подходами, повторами и весом (форматтеры `SetFormat` из E2), «прошлый раз» по каждому упражнению (последние подходы по справочнику, E2), тап по упражнению — прогресс E3 (`exercise_progress/{catalogId}`), большая кнопка «Начать».
5. Пока идёт сессия: на просмотре **другой** тренировки кнопки «Начать» нет; у каждого упражнения кнопка «+ в сегодняшнюю» — копия упражнения в **конец** текущей сессии **только на сегодня** (тренировка в БД не меняется). До него доходят через существующую шторку выбора упражнения. Подходы добавленного упражнения пишутся в историю и прогресс как обычно (через `catalogId`). На просмотре **самой** идущей тренировки вместо «Начать» — «Вернуться к тренировке».
6. Виджет: без сессии — сразу запускает тренировку (без экрана просмотра, как сейчас); при идущей сессии — возвращает в неё. `ActiveWorkoutTracker` заменяется менеджером сессии.
7. Архитектура: логика сессии переезжает из `WorkoutExecutionViewModel` в `@Singleton WorkoutSessionManager` (корутины в app-scope). ViewModel экрана выполнения — тонкий адаптер. Плашка рисуется над `NavHost`. Схема БД не меняется.
8. Порядок: сначала перенос логики с переносом тестов (поведение не меняется), затем плашка и сворачивание, затем экран просмотра и «+ в сегодняшнюю».
9. После завершения тренировки (экран Finished) сессия закрывается, плашки нет.

Смерть процесса = потеря идущей тренировки, как сейчас. Сохранять сессию между запусками процесса пользователь явно отказался.

## Вне рамок

- Переживание смерти процесса, сохранение незавершённой сессии в БД.
- Изменение состава тренировки в БД из сессии (добавленное упражнение не попадает в шаблон).
- Удаление и перестановка упражнений внутри сессии; добавление упражнения «вручную», не из другой тренировки.
- Плавающее окно, жесты сворачивания свайпом, анимация «перетекания» плашки в экран.
- Новые уведомления. Поведение `TimerNotificationService` не меняется, меняется только цель тапа.

## Архитектура

### `WorkoutSessionManager`

Новый класс `presentation/session/WorkoutSessionManager.kt`, `@Singleton`, `@Inject constructor`. Живёт в слое `presentation`, как `SoundPlayer` и `WakeLockHelper`: он запускает сервис уведомлений и держит Android-зависимости.

**Зависимости** — ровно те, что сейчас у ViewModel, без `ActiveWorkoutTracker`, плюс область корутин:

```kotlin
@Singleton
class WorkoutSessionManager @Inject constructor(
    @ApplicationContext private val context: Context,
    private val soundPlayer: SoundPlayer,
    private val getWorkoutByIdUseCase: GetWorkoutByIdUseCase,
    private val vibrationManager: VibrationManager,
    private val wakeLockHelper: WakeLockHelper,
    private val workoutRepository: WorkoutRepository,
    private val finishWorkoutSessionUseCase: FinishWorkoutSessionUseCase,
    @ApplicationScope private val scope: CoroutineScope
)
```

**Область корутин.** Новый модуль `di/CoroutineScopeModule.kt` с квалификатором `@ApplicationScope` отдаёт `CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)`, `@Singleton`. Почему `Main`: сейчас всё состояние ViewModel меняется на главном потоке (`viewModelScope` = `Main.immediate`), и поля без синхронизации (`isFinishing`, `finishPending`, `_recordedSets`) рассчитаны на это; запись в БД переключает поток внутри Room. Почему `SupervisorJob`: сбой одной корутины (например, записи заметки) не должен отменять таймер отдыха. Тесты передают свою область (`TestScope`/`CoroutineScope(UnconfinedTestDispatcher())`), поэтому `Dispatchers.setMain` в тестах менеджера не нужен. `SoundPlayer`, `WakeLockHelper`, `VibrationManager` — не синглтоны; менеджер держит свои экземпляры всё время жизни процесса, это нормально.

### Состояние

```kotlin
/** Упражнение сессии. Позиция в списке — ключ: список только дописывается в конец. */
data class SessionExercise(
    val exercise: Exercise,
    val addedToday: Boolean      // копия из другой тренировки («+ в сегодняшнюю»)
)

sealed interface WorkoutSession {
    data object None : WorkoutSession

    data class Present(
        val workoutId: Int,
        val workoutName: String,
        val exercises: List<SessionExercise>,
        val exerciseIndex: Int,
        val phase: WorkoutExecutionState,   // Loading / Error / Rest / Active / Finished
        val restOver: Boolean,              // Active наступил сам по истечении отдыха
        val isFinishing: Boolean            // идёт запись завершённой сессии
    ) : WorkoutSession
}
```

Публичный API менеджера:

```kotlin
val session: StateFlow<WorkoutSession>
val finishError: StateFlow<Boolean>

/** Сессия идёт: Loading, Rest или Active. Error, Finished и None — не идёт. */
val isRunning: Boolean
val isLastSetOfWorkout: Boolean

fun start(workoutId: Int)            // идемпотентен, см. ниже
fun skipRest()
fun onExerciseFinished()
fun moveToExercise(index: Int)
fun updateExerciseNote(index: Int, note: String)
fun updateExerciseWeightAndReps(index: Int, weight: Double, extraWeight: Double, reps: Int)
fun addExerciseToday(exercise: Exercise): AddResult   // ADDED / ALREADY_ADDED / NO_SESSION
fun registerInteraction()            // тап по плашке, см. «Учёт простоя»
fun dismissFinishError()
fun abandon()                        // выход без сохранения
fun close()                          // закрыть Finished / Error / Loading
```

`internal` для тестов, как сейчас: `recordedSets`, `lastInteractionAt`, `excludedIdleMillis`, `isIdleReminderJobActive`, `onRestFinished()`, `registerInteraction(now)`.

**Почему один `StateFlow`.** Сейчас `exercises`, `exerciseIndex`, `workoutName` — обычные поля, которые экран читает во время композиции (`WorkoutExecutionScreen.kt:151`, `:257`); перерисовку им обеспечивает смена `uiState`. Добавление упражнения с другого экрана меняет список без смены фазы, и шторка выбора его бы не увидела. Один снимок исключает и рассинхрон «индекс уже новый, список ещё старый».

**Почему индекс, а не `exercise.id`.** После «+ в сегодняшнюю» в сессии может оказаться строка из другой тренировки, а одно и то же упражнение — дважды, если пользователь добавит его ещё раз позже (см. правило повторов). Сейчас по `exercise.id` ищут `moveToSelectedExercise` (`:401`), `updateExerciseNote` (`:428`), `updateExerciseWeightAndReps` (`:460`) и сравнения в `_uiState.update` (`:439`, `:446`, `:471`, `:474`). Список сессии только растёт в конец и никогда не переставляется, поэтому позиция — стабильный ключ. Все эти места переходят на индекс; `exercise.id` остаётся только аргументом записи в БД (`workoutRepository.updateExercise…`), и только для строк шаблона.

**`start(workoutId)`:**

- `None`, `Finished` или `Error` → новая сессия: `Loading`, затем загрузка, как в `loadWorkout()` (`:140`), и `Active` первого упражнения или `Error`. Загрузка — в `@ApplicationScope`; её `Job` хранится, чтобы `close()` мог её отменить.
- Идёт сессия **этой же** тренировки → ничего не делает. Это чинит и тихую ошибку сегодняшнего кода: `LaunchedEffect(workoutId)` (`WorkoutExecutionScreen.kt:90`) перезапускается при пересоздании активности (смена темы системы, языка, размера шрифта; поворот запрещён манифестом), и `loadWorkout()` обнуляет сессию посреди тренировки.
- Идёт сессия **другой** тренировки → ничего не делает; экран выполнения показывает идущую сессию. Штатно сюда не попасть (см. «Навигация»), это страховка.

**`abandon()`** — всё, что сейчас делает `onCleared()`, плюс сброс состояния: отменить `timerJob`, `idleReminderJob` и загрузку, `wakeLockHelper.release()`, `stopNotification()`, `soundPlayer.release()`, очистить подходы и флаги, `session = None`, `finishError = false`. В БД ничего не пишется. Уведомления «Отдых завершён» и «Вы всё ещё тренируетесь?», если уже показаны, не снимаются — как сейчас при выходе.

**`close()`** — то же, что `abandon()`, но допустим только в `Loading`, `Error`, `Finished`; в `Rest`/`Active` ничего не делает (защита от случайного сброса идущей тренировки).

### Тонкая ViewModel экрана выполнения

`WorkoutExecutionViewModel` остаётся `@HiltViewModel`, зависит только от менеджера:

- `uiState: StateFlow<WorkoutExecutionState>` — `session.map { (it as? Present)?.phase ?: Loading }.stateIn(viewModelScope, Eagerly, …)`; плюс `stateIn`-производные для шапки: название, номер и число упражнений, список для шторки.
- `finishError`, `isLastSetOfWorkout` — проброс.
- `start(workoutId)`, действия — проброс в менеджер.
- `onCleared()`: если `!manager.isRunning` → `manager.close()`. Если сессия идёт — ничего: экран свернули.

Диалоги и шторки (`showNoteDialog`, `currentEditingExercise`, `showExitDialog`, `showFinishDialog`, `showExercisePicker`, `weightSheetExercise`, `WorkoutExecutionScreen.kt:78-83`) остаются `remember`-состоянием экрана, как сейчас. При сворачивании они закрываются, при возврате экран открывается чистым — это ожидаемо. Шторка веса и диалог заметки запоминают **индекс** упражнения на момент открытия, а не объект `Exercise`.

### Что зависело от жизни ViewModel

| Сейчас | Триггер сейчас | Триггер после |
|---|---|---|
| Снять wakelock, погасить уведомление отдыха, отпустить `SoundPlayer`, отменить напоминание | `onCleared()` — уход с экрана = выход | `abandon()` (× на плашке, «Выйти без сохранения») или `close()` (уход с Finished/Error/Loading). Сворачивание **ничего не снимает**: таймер, wakelock и уведомление продолжают работать |
| Отметка «тренировка идёт» для виджета | `ActiveWorkoutTracker.start/stop` | `manager.isRunning` |
| Отмена записи сессии при уходе с экрана | `viewModelScope` отменял корутину записи | Запись в `@ApplicationScope` не отменяется; уйти во время записи нельзя (см. «Сворачивание») |
| Отмена загрузки при уходе с экрана | `viewModelScope` | `onCleared()` → `close()` отменяет загрузку |
| Перезапуск сессии при пересоздании активности | `LaunchedEffect` → `loadWorkout()` | `start()` идемпотентен — сессия не сбрасывается |

## Сохранение поведения

Всё ниже переносится без изменения логики; тесты (раздел «Тестирование») фиксируют каждое правило.

- **Таймер отдыха**: тик 200 мс по `System.currentTimeMillis()`, уведомление обновляется раз в секунду, по окончании — звук `R.raw.timer`, вибрация, снятие wakelock, уведомление «Отдых завершён», переход в `Active`. Wakelock берётся на время отдыха + 5 с.
- **Пропуск отдыха**: отмена таймера, снятие wakelock и уведомления, `Active` с весом и повторами из упражнения, взвод напоминания.
- **Напоминание о простое**: 5 мин в `Active`, сервис запускается best-effort с перехватом `IllegalStateException`. Взводится при входе в `Active`, отменяется в `Rest`, `Finished` и при `abandon()`/`close()`. Пока тренировка свёрнута, напоминание работает так же, как при открытом экране.
- **Учёт простоя**: разрыв между действиями сессии длиннее 10 мин исключается из длительности сверх порога. Действия сессии — те же, что сейчас (`onExerciseFinished`, `skipRest`, `moveToExercise`, правки заметки и веса), плюс `addExerciseToday` и тап по плашке (см. ниже). Автоматическое окончание отдыха действием не считается. Простое разглядывание других экранов действием не считается.
- **Подтверждение последнего подхода**: экран спрашивает, если `isLastSetOfWorkout`; семантика уточнена в «+ в сегодняшнюю».
- **Завершение**: синхронный `isFinishing` против двойного нажатия; при сбое — подходы остаются, `finishPending`, снекбар «Не удалось сохранить тренировку», повтор не дублирует последний подход; при успехе — `Finished(durationMillis)`, затем `updateLastUseAt(workoutId)` (порядок из комментария `:384-390` сохраняется).
- **Правка плиток**: сначала состояние, потом БД; во время отдыха правка относится к следующему подходу.
- **Переход по шторке**: сбрасывает `finishPending`, гасит таймер, `Active` с подхода 1.

## Сворачивание и выход

### Экран выполнения

- **«Назад»** (системный, `BackHandler`) и **стрелка** в шапке в `Rest`/`Active` сворачивают: `navController.popBackStack()`. Без диалога. Описание стрелки для TalkBack — «Свернуть тренировку».
- В `Loading`, `Error`, `Finished` «Назад» работает как сейчас — просто уходит; `onCleared()` закрывает сессию.
- **Пока идёт запись завершения** (`isFinishing`) «Назад» и стрелка ничего не делают: запись длится доли секунды, а свернуть посреди неё значило бы получить `Finished`, которого никто не увидит.
- **Меню ⋮** занимает пустое место справа в шапке (`Box(Modifier.size(48.dp))`, `WorkoutExecutionScreen.kt:163`). Один пункт — «Выйти без сохранения» → прежний диалог выхода (`execution_exit_title`, `execution_exit_message`, «Выйти» / «Отмена») → `abandon()` и `popBackStack()`. Меню видно только в `Rest`/`Active` и скрыто при `isFinishing`.
- Если `popBackStack()` вернул `false` (экран выполнения — единственная запись; штатно не бывает, диплинк строит стек «список → выполнение»), переходим на список с `popUpTo(Execution) { inclusive = true }`.

Прежний `BackHandler` с диалогом (`:94`) и логика `hasUnsavedProgress` в стрелке (`:139`) удаляются.

### Плашка

**Размещение.** Новый composable `presentation/session/MiniWorkoutBar.kt`. Корень навигации (`NavGraph`) становится колонкой:

```
Column(fillMaxSize) {
    NavHost(Modifier.weight(1f) + consumeWindowInsets(navigationBars), когда плашка видна)
    MiniWorkoutBar(Modifier.navigationBarsPadding())   // когда видна
}
```

Плашка «над NavHost» в иерархии, но **под** ним по раскладке: она не перекрывает контент экранов, FAB списка и снекбары оказываются выше неё сами. Отступ системной навигации берёт на себя плашка, а экраны внутри `NavHost` его не добавляют повторно (Material3 `Scaffold` учитывает уже поглощённые отступы). Модальные шторки и диалоги — отдельные окна и ложатся поверх плашки, это нормально.

**Когда видна** — все условия сразу:

- `session` — `Present` с фазой `Rest` или `Active`;
- текущий маршрут не `Screen.Execution.route` (по `currentBackStackEntryAsState()`);
- клавиатура не открыта (`WindowInsets.isImeVisible`): в редакторе и поиске плашка не нужна и прыгала бы над клавиатурой.

Появление и исчезновение — `AnimatedVisibility` со сдвигом снизу, 150–200 мс.

**Раскладка.** Высота 64 dp, фон `surface`, верхняя граница `outline` 1 dp (как у карточек темы). Слева кольцо 28 dp в зоне 48 dp, в середине две строки, справа `IconButton` × (48 × 48 dp).

- Строка 1 — название тренировки, `labelMedium`, `onSurfaceVariant`, одна строка с многоточием.
- Строка 2 — статус, `titleSmall`, одна строка с многоточием:

| Состояние | Текст | Кольцо |
|---|---|---|
| `Rest` | «Отдых 01:18» (`DateFormatter.formatDurationCompact`, тот же формат, что у `RestRing`) | дуга `primary` = оставшаяся доля отдыха на дорожке `outline`, как `RestRing` в малом размере |
| `Active`, `restOver = false` | «Подход 2 из 4 · Жим лёжа» | полная дорожка `outline`, без дуги |
| `Active`, `restOver = true` | «Пора: подход 2», цвет `primary` | сплошное кольцо `primary` |

`restOver` поднимается в `onRestFinished()` и опускается на любом действии, меняющем фазу или подход (`onExerciseFinished`, `moveToExercise`, `skipRest`). После `skipRest()` — обычный «Подход N из M»: пользователь сам начал подход. Плашка не мигает и не анимирует кольцо по кругу: сигнал «пора» уже дали звук, вибрация и уведомление.

**Тап и доступность.** Вся плашка, кроме ×, — одна кликабельная зона высотой 64 dp: `Modifier.clickable(onClickLabel = «Вернуться к тренировке», role = Button)` с `semantics(mergeDescendants = true)`. TalkBack читает «Ноги, Отдых 01:18, кнопка, двойное нажатие — вернуться к тренировке». `liveRegion` не ставится: отсчёт менялся бы вслух каждую секунду. Кнопка × — отдельный узел, описание «Выйти из тренировки без сохранения».

**Крестик.** × → тот же диалог «Выйти из тренировки? / Прогресс не будет сохранён.» с «Выйти» / «Отмена». Диалог живёт в корне навигации рядом с плашкой. «Выйти» → `abandon()`; плашка исчезает, текущий экран остаётся.

**Частота перерисовки.** Во время отдыха `session` меняется каждые 200 мс. Плашка читает поток через `collectAsStateWithLifecycle()` и пересобирается сама; корень навигации подписан только на производный `Boolean` «плашка видна» (`distinctUntilChanged`), чтобы тик не перерисовывал `NavHost`.

## Навигация

### Возврат в тренировку

Инвариант: **запись экрана выполнения в стеке — либо на вершине, либо её нет.** С экрана выполнения никуда не переходят (только шторки и диалоги), а сворачивание её снимает. Поэтому дубликатов не бывает.

Возврат (тап по плашке, «Вернуться к тренировке» на просмотре, виджет и уведомление при идущей сессии) — одна функция в `NavGraph`:

```kotlin
navController.navigate(Screen.Execution.createRoute(session.workoutId)) { launchSingleTop = true }
```

Стек после возврата — тот, что был, плюс выполнение сверху: например, «список → просмотр «Спина» → выполнение «Ноги»». «Назад» снова сворачивает и возвращает на просмотр «Спины», как в музыкальном плеере. `launchSingleTop` страхует от двойного тапа.

Экран выполнения при входе вызывает `start(workoutId)`; для идущей сессии этой тренировки это no-op, и экран сразу показывает текущую фазу.

### Виджет и уведомления

`MainActivity` вместо `ActiveWorkoutTracker` получает `WorkoutSessionManager` и отдаёт в `NavGraph` событие «вернуться к тренировке» (как сейчас `newIntent`).

- **`onNewIntent`, сессия идёт** (`isRunning`): интент виджета (диплинк `workouttimer://execution/{id}`) или уведомления (новый `action`, ниже) → событие возврата. Диплинк **не разбирается**: `handleDeepLink` перестроил бы стек. Если сессия идёт по другой тренировке — возврат в неё (решение 6). Сейчас (`MainActivity.kt:56`) такой интент просто отбрасывался, и это работало, потому что экран выполнения всегда был наверху; со сворачиванием пользователь может стоять на любом экране.
- **`onNewIntent`, сессии нет**: виджет — как сейчас (`handleDeepLink`, запуск без экрана просмотра); уведомление — ничего, приложение просто выходит вперёд.
- **`onCreate` при идущей сессии.** Процесс жив, а активность пересоздана: пользователь свернул тренировку и закрыл приложение «Назад» со списка (на API < 31 это завершает активность), а потом тапнул виджет. `NavController` сам разобрал бы диплинк из стартового интента в `setGraph()` и открыл бы выполнение **другой** тренировки. Поэтому в `onCreate`, до `setContent`, если `isRunning` и у интента есть диплинк выполнения: `intent.data = null` (через `setIntent` с копией без данных) и событие возврата. Холодный старт после смерти процесса не затронут: сессии нет.
- **Уведомления** (`TimerNotificationService.kt:113`, `:147`, `:195`): `PendingIntent` получают `action = ACTION_OPEN_ACTIVE_WORKOUT` (константа в `MainActivity`), флаги прежние. Тап при идущей сессии возвращает в неё, даже если пользователь стоит на другом экране. Тап по устаревшему «Отдых завершён» после выхода из тренировки просто открывает приложение.

`ActiveWorkoutTracker` и `ActiveWorkoutTrackerTest` удаляются. Комментарии в `NavGraph.kt:32-37` и `QuickStartWidget.kt:146-152` переписываются под менеджер; сам виджет не меняется.

### Новый маршрут

`Screen.WorkoutPreview` — `workout/{workout_id}`, `IntType`, по образцу `Screen.History`. Диплинка нет.

- Тап по строке списка (`ListWorkoutScreen.kt:344`) → `workout/{id}`.
- «Начать» на просмотре → `navigate(Execution.createRoute(id)) { popUpTo(WorkoutPreview.route) { inclusive = true } }`: просмотр заменяется выполнением, и «Назад» (сворачивание) ведёт на список — как сегодня после старта из списка.

### «+ в сегодняшнюю»

Кнопка — `TextButton` с иконкой «+» справа в строке, зона нажатия ≥ 48 dp, описание «Добавить «Жим лёжа» в сегодняшнюю тренировку». Тап → `manager.addExerciseToday(exercise)`:

- **В конец** списка сессии добавляется `SessionExercise(exercise.copy(), addedToday = true)` — копия шаблона из другой тренировки целиком: подходы, повторы, вес, добавка, единица, отдых, заметка, `catalogId`. Текущий индекс и фаза не меняются. Засчитывается как действие для учёта простоя.
- Результат `ADDED` → снекбар «Жим лёжа — в сегодняшней тренировке», кнопка у строки становится неактивной «Добавлено».
- **Повтор того же упражнения.** Копия одного и того же упражнения (по `exercise.id` исходной строки) добавляется в сессию **один раз**: второй вызов возвращает `ALREADY_ADDED`, кнопка уже неактивна. Защищает от двойного тапа и случайного дубля. Тот же `catalogId`, уже есть в сегодняшней тренировке (другая строка с тем же упражнением), не мешает: у строк разные шаблоны, подходы обеих пишутся в одну запись справочника, как разрешено в E1.
- **Нет идущей сессии** (`None`, `Loading`, `Error`, `Finished`, а также `isFinishing`) → `NO_SESSION`, ничего не меняется. Кнопки в этих состояниях и не видно; проверка — страховка от гонки.
- **В шторке выбора** добавленные упражнения стоят в конце с меткой «сегодня»; сегменты прогресса и «n/m» в шапке считают их вместе с остальными.
- **Правка веса, повторов и заметки** у добавленного упражнения меняет **только сессию**: в БД ничего не пишется. Иначе правка посреди «Ног» молча меняла бы шаблон «Спины». У строк шаблона правки по-прежнему пишутся в шаблон.
- **Подходы** добавленного упражнения — обычные `RecordedSet` с его `catalogId`; при завершении уходят в сессию идущей тренировки и видны в её истории и в прогрессе упражнения. `lastUseAt` исходной тренировки не трогается.

**Последний подход.** `isLastSetOfWorkout` = текущий подход последний **и** `exerciseIndex == exercises.lastIndex` по **текущему** списку. Если упражнение добавили, когда пользователь стоял на последнем подходе, признак сам становится ложным: «Закончить подход» запишет подход и уведёт на отдых перед добавленным упражнением, без диалога завершения.

**Добавление после сбоя записи.** Сейчас `finishPending` (`:86`) живёт до успешной записи или перехода по шторке. Если после сбоя добавить упражнение и нажать «Закончить подход», последний подход заменится (верно — это тот же подход), но флаг остался бы поднятым, и **следующий** подход добавленного упражнения тоже заменил бы предыдущий вместо дописывания. Поэтому правило уточняется: `onExerciseFinished()` снимает `finishPending` сразу после того, как использовал его для замены; ветка завершения поднимает его снова. Для существующих сценариев ничего не меняется (повтор после сбоя снова идёт в ветку завершения).

## Ошибки и краевые случаи

- **Правка идущей тренировки в редакторе.** `updateWorkout` удаляет и заново вставляет упражнения (`WorkoutDao.kt:161`), их id меняются; правки веса и заметки из сессии потом пишутся по старым id и молча теряются, а сохранение редактора затирает то, что сессия успела записать. Поэтому вход в редактор идущей тренировки закрыт (выше). Других путей в `edit_workout/{id}` нет.
- **Удаление идущей тренировки** закрыто тем же правилом. Без него сессия дописалась бы с `workoutId` удалённой тренировки (FK нет, история недоступна), `updateLastUseAt` ничего бы не сделал.
- **Правка или удаление тренировки-источника** добавленного упражнения разрешены: в сессии лежит копия. Если автоочистка справочника удалит запись, `finishSession` найдёт или создаст её по названию (`WorkoutDao.kt:182`), подходы не теряются.
- **Переименование или смена единицы в «Упражнениях»** во время сессии: в сессии остаются прежние название и единица; подходы пишутся с `catalogId` (связь не рвётся) и с единицей снимка — в прогрессе они видны со своей подписью, как любые подходы в другой единице.
- **Смерть процесса** — сессия теряется, плашки нет, уведомление отдыха исчезает с процессом (`START_NOT_STICKY`). Свёрнутая тренировка в фазе `Active` не держит ни сервиса переднего плана, ни wakelock, поэтому в фоне её могут убить так же, как сейчас приложение с открытым экраном выполнения. Принятая потеря.
- **Пересоздание активности** (смена темы, языка, шрифта; поворот запрещён): менеджер и ViewModel живы, `start()` идемпотентен — сессия не сбрасывается (сейчас сбрасывается).
- **Закрытие приложения «Назад» со списка при свёрнутой тренировке.** На API 31+ система уводит задачу в фон; на старых версиях активность завершается, процесс живёт, сессия продолжается. При новом запуске плашка на месте; виджет и уведомление возвращают в тренировку (см. `onCreate`).
- **Новый старт с виджета при идущей сессии** — возврат в идущую (решение 6), независимо от того, какую тренировку показывает виджет.
- **Экран Finished.** `Finished` не считается идущей сессией: плашки нет, виджет и «Начать» работают как без сессии. Сессия закрывается, когда запись экрана уходит из стека («На главную» или «Назад») — через `onCleared()` → `close()`. Если `Finished` по какой-то причине останется висеть, `start()` его заменит.
- **Ошибка загрузки** (`Error`) — сессия не идёт; «Повторить» вызывает `start()` заново; уход закрывает сессию.
- **Уход с экрана во время загрузки** — `close()` отменяет загрузку, плашка не появляется.
- **Сбой завершения, затем сворачивание.** `finishError` хранится в менеджере; снекбар покажется при возврате на экран выполнения, если не был показан. Подходы и `finishPending` на месте.
- **Ошибка записи заметки или веса в БД** — как сейчас: исключение в корутине. Под `SupervisorJob` оно не роняет таймер, но и не обрабатывается; поведение не ухудшается (сейчас `viewModelScope` ведёт себя так же). Обработчик исключений области логирует его.

- **`WorkoutExecutionViewModelTest`** (новый, короткий): `onCleared` при идущей сессии её не трогает; в `Finished`, `Error`, `Loading` — вызывает `close()`; `uiState` повторяет фазу менеджера.
- **`WorkoutPreviewViewModelTest`**: состояние кнопки по таблице (нет сессии / эта / другая / `Loading` / `Finished`); «прошлый раз» группируется по `catalogId` и берёт последнюю сессию; удалённая тренировка → «не найдена»; пустая → без «Начать»; отметка «Добавлено» после `ADDED`.
- **`ScreenDeepLinkTest`** — маршрут `workout/{id}`; разбор интента в `MainActivity` вынести в чистую функцию (`resolveIntent(intent, isRunning) → OpenDeepLink / ReturnToSession / Ignore`) и покрыть: виджет без сессии, виджет при сессии другой тренировки, уведомление с сессией и без.

Эмулятор (только `emulator-5554`, `connectedAndroidTest` сносит приложение):

- **Compose, плашка** (`MiniWorkoutBarContent` без менеджера): три текста статуса; × вызывает обработчик выхода, тап по плашке — возврата; высота зоны тапа и × ≥ 48 dp (`assertTouchHeightIsAtLeast`); объединённое описание и `onClickLabel`.
- **Compose, просмотр** (`WorkoutPreviewContent`): «Начать» / «Вернуться к тренировке» / подсказка и «+ В сегодняшнюю» по состоянию; «Добавлено» неактивна; тап по строке отдаёт `catalogId`; «прошлый раз» и «Ещё не делали».
- **Навигация** (`TestNavHostController` с настоящим графом): свернуть → открыть просмотр → вернуться через плашку → в стеке одна запись выполнения; повторный возврат не добавляет вторую; «Назад» с выполнения после возврата ведёт на просмотр.
- **Ручной сценарий:**
  1. Начать «Ноги», закончить подход, во время отдыха «Назад» — плашка «Отдых 01:5x», отсчёт идёт, уведомление обновляется.
  2. Экран погашен до конца отдыха — звук, вибрация, «Отдых завершён»; на плашке «Пора: подход 2».
  3. Открыть «Спину» → «прошлый раз» совпадает с историей; «+ В сегодняшнюю» у одного упражнения → снекбар, кнопка «Добавлено»; тап по упражнению → прогресс.
  4. Плашка → выполнение; шторка показывает добавленное с меткой «сегодня»; дойти до него, поправить вес, закончить подход; в шаблоне «Спины» вес прежний.
  5. Последний подход «Ног» после добавления — без диалога завершения; последний подход добавленного — с диалогом; Finished, плашки нет; в истории «Ног» есть подходы добавленного, в прогрессе упражнения — тоже.
  6. × на плашке → «Выйти» → плашки нет, уведомление погасло, в истории ничего нового. То же через ⋮ «Выйти без сохранения».
  7. Свернуть, тапнуть виджет с другой тренировкой → открылось выполнение идущей. Закрыть приложение «Назад» со списка, тапнуть виджет — то же.
  8. Тап по уведомлению отдыха со стоящего экрана «Упражнения» → выполнение.
  9. Сменить тему системы и размер шрифта посреди тренировки — сессия не сбросилась.
  10. Плашка не перекрывает FAB списка, снекбар «Пропущено», последнюю строку списка; отступ навигационной панели один (жестовая и трёхкнопочная навигация); при открытой клавиатуре в поиске плашки нет.
  11. TalkBack: плашка читается одной фразой, × — отдельно.
  12. В меню идущей тренировки «Редактировать» и «Удалить» неактивны.

## Порядок выпуска

Три PR; после каждого приложение цельное. Схема БД не меняется ни в одном.

1. **M1 — менеджер сессии (поведение не меняется).**
   1. `@ApplicationScope` и `CoroutineScopeModule`.
   2. `WorkoutSessionManager` с состоянием-снимком, индексами вместо `exercise.id`, `start` (идемпотентный), `abandon`, `close`, `isRunning`; `WorkoutExecutionState` переезжает в `presentation/session/`.
   3. Перенос `WorkoutExecutionViewModelTest` в `WorkoutSessionManagerTest` — сначала тесты, потом код; новые тесты `start`/`abandon`/`close`/`isRunning`.
   4. Тонкая ViewModel. В M1 её `onCleared()` вызывает `abandon()` при идущей сессии — уход с экрана по-прежнему завершает тренировку, «Назад» по-прежнему спрашивает подтверждение.
   5. `MainActivity` на `isRunning`; удаление `ActiveWorkoutTracker` и его теста.
   Видимое изменение одно: смена темы/шрифта больше не сбрасывает тренировку.
2. **M2 — сворачивание и плашка.**
   1. `onCleared()` закрывает только не идущую сессию; «Назад» и стрелка сворачивают, блокировка во время записи; меню ⋮ «Выйти без сохранения».
   2. `restOver`; `MiniWorkoutBar` в корне навигации, видимость, отступы, диалог ×.
   3. Функция возврата; `MainActivity.onNewIntent`/`onCreate` и `ACTION_OPEN_ACTIVE_WORKOUT` в уведомлениях.
   4. Блокировка правки и удаления идущей тренировки в списке.
   5. Временное правило до M3: тап по строке списка и «НАЧАТЬ» при идущей сессии **возвращают** в неё (как виджет), а не открывают выполнение другой тренировки.
   6. Compose-тесты плашки, навигационный тест, ручные пункты 1, 2, 6–11.
3. **M3 — просмотр и «+ в сегодняшнюю».**
   1. `ObserveWorkoutUseCase`, маршрут `workout/{workout_id}`, `WorkoutPreviewViewModel` и экран.
   2. Список: тап → просмотр, правила «НАЧАТЬ» / «ВЕРНУТЬСЯ» и пунктов меню.
   3. `addExerciseToday`, `SessionExercise.addedToday`, правки только в сессии, уточнённый сброс `finishPending`, метка «сегодня» в шторке.
   4. Тесты менеджера на добавление, тесты ViewModel просмотра, Compose-тесты просмотра, ручные пункты 3–5.
